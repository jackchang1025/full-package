  Android 逆向工程成熟方案调研报告

  项目背景

  - 目标 APK: stripchat-release.apk (47MB, package com.guard.wallet)
  - 混淆: ProGuard (标准级别，非加壳/加固)
  - 规模: 327 核心文件, ~57K 行代码
  - 目标: 产出可读、可维护、可二次开发的 Java 源码
  - 已尝试: JADX / CFR / Vineflower
  直接反编译→编译，均失败（空桩或上千编译错误）

  ---
  方案一：Apktool Smali 修改流 (推荐度: ★★★★★)

  原理: 不走 DEX→Java→编译 这条路，而是 DEX→Smali→修改→重打包

  工具链: Apktool + baksmali/smali + jadx-gui(辅助阅读)

  工作流:
  1. apktool d app.apk → 得到 smali 代码 + 资源文件
  2. 用 jadx-gui 阅读 Java 伪代码理解逻辑
  3. 在 smali 层面做修改（改路由、改配置、加 hook 点）
  4. apktool b output/ -o modified.apk → 重打包
  5. 签名 → 安装测试

  优势:
  - 100% 可重打包，这是 Android 逆向的标准生产流程
  - 不存在"编译不过"的问题，因为根本不需要编译 Java
  - Apktool 是最成熟的工具（10+ 年历史，持续维护）
  - smali 是 Dalvik 字节码的 1:1 文本表示，无信息丢失

  劣势:
  - smali 可读性远低于 Java，需要学习 smali 语法
  - 大规模重构困难，适合定点修改

  适用场景: 改配置、改路由、加日志、替换服务端地址 — 正好匹配你的需求

  成本: 免费开源

  ---
  方案二：jadx-gui 交互式 + Frida 动态分析 (推荐度: ★★★★☆)

  原理: jadx-gui 做静态阅读和语义重命名，Frida 做运行时 hook 验证

  工具链: jadx-gui + Frida + jadx --deobf 输出

  工作流:
  1. jadx-gui 打开 APK，交互式重命名混淆类/方法/字段
  2. 重命名会自动传播到所有引用
  3. 导出重命名后的 Java 源码作为参考文档
  4. Frida hook 关键方法，运行时验证逻辑理解是否正确
  5. 基于理解，在 smali 层或新项目中实现修改

  优势:
  - jadx-gui 的重命名是全局传播的，一次改名所有引用同步更新
  - Frida 可以在运行时拦截任何方法，打印参数和返回值
  - 不需要代码能编译，纯阅读+理解+验证
  - 已安装: jadx 1.5.1 + Frida 17.9.1

  劣势:
  - 产出是"理解"而非"可编译代码"
  - Frida 需要 root 设备或 frida-gadget 注入
  - 适合分析，不直接产出可运行的修改版 APK

  适用场景: 深度理解代码逻辑、验证混淆函数行为、为方案一/三提供知识基础

  成本: 免费开源

  ---
  方案三：Simplify 去混淆预处理 + 反编译 (推荐度: ★★★★☆)

  原理: 先用 Simplify 虚拟执行 DEX，优化掉混淆层，再反编译

  工具链: Simplify + jadx/CFR

  工作流:
  1. simplify -i classes.dex -o simplified.dex — 虚拟执行并优化
  2. 常量传播：把 String.valueOf(new char[]{(char)72, (char)101}) → "He"
  3. 死代码消除：删除不可达分支
  4. 反射还原：Method.invoke() → 直接调用
  5. 用 jadx/CFR 反编译优化后的 DEX

  优势:
  - 从根源上简化字节码，而非修补反编译输出
  - 对 ProGuard 的字符串加密、反射调用特别有效
  - 处理后的 DEX 反编译质量显著提升
  - 免费开源

  劣势:
  - 不重命名类/方法（仍需配合 jadx --deobf）
  - 复杂代码可能超时
  - 需要 JDK 8 构建

  适用场景: 作为反编译前的预处理步骤，与方案一/二组合使用

  成本: 免费开源

  ---
  方案四：JEB Decompiler 商业方案 (推荐度: ★★★☆☆)

  原理: 商业级反编译器，内置高级去混淆优化器

  工具链: JEB Decompiler (PNF Software)

  核心能力:
  - Dalvik 反编译器（含多 DEX 支持）
  - 内置优化器：自动解密字符串、还原反射调用、清理混淆代码
  - 交互式重命名 + 交叉引用
  - 内置 Dalvik 和 Native 调试器
  - 脚本 API (Python/Java) 支持批量自动化

  优势:
  - 反编译质量业界最高，专门针对混淆代码优化
  - 自动去混淆能力远超免费工具
  - 专业支持和持续更新

  劣势:
  - 价格高：JEB Android $1,200/年 或 $140/月，JEB Pro $2,000/年
  - 仍然不保证产出可编译的 Java（这是所有反编译器的固有限制）
  - 学习曲线

  适用场景: 预算充足、需要深度分析高度混淆代码

  成本: $1,200-$2,000/年

  ---
  方案五：Recaf 字节码直接编辑 (推荐度: ★★★☆☆)

  原理: 直接在 Java 字节码层面编辑，内置编译器可处理缺失依赖

  工具链: Recaf + dex2jar + jar2dex

  工作流:
  1. dex2jar 转换 DEX → JAR
  2. Recaf 打开 JAR，内置多个反编译器查看代码
  3. 直接在反编译视图中编辑 Java 代码
  4. Recaf 内置编译器编译修改的类（能处理部分缺失引用）
  5. 导出修改后的 JAR → jar2dex → 重打包

  优势:
  - 内置编译器能在缺失依赖时编译单个类
  - 不需要整个项目能编译，只编译你修改的类
  - 去混淆工具：批量重命名 + 字节码变换器
  - 免费开源

  劣势:
  - 主要面向 Java JAR，Android DEX 支持需要额外转换步骤
  - 大规模修改仍然困难

  适用场景: 需要修改少量关键类的逻辑

  成本: 免费开源

  ---
  方案六：Bytecode Viewer 多引擎对比 (推荐度: ★★☆☆☆)

  原理: 集成 6 个反编译器，同时查看对比选最优输出

  适用场景: 辅助阅读，不作为主力方案

  成本: 免费开源

  1. 评估维度偏离了核心问题

  过"。

  一个文件可以是 A 级可读性，但它引用了 50 个混淆类，那些类又引用了更多 —
  编译是全局问题，不是单文件问题。评估报告完全忽略了这个级联依赖。

  2. 把"可读"等同于"可编译"

  评估报告说 199 个文件是 A

● jadx-gui + Frida 实现 vendor APK 一比一复刻：可行性评估

  先明确目标

  用 jadx-gui 静态阅读 + Frida 动态 hook，彻底理解 vendor
  每个模块的逻辑，然后在全新项目中用干净 Java 从零重写，实现功能一比一。

  可行性结论：可行，但要对工作量有清醒认识

  jadx-gui 能做什么：
  - 交互式重命名混淆类/方法/字段，全局传播
  - 交叉引用追踪（谁调用了这个方法、这个字段在哪被赋值）
  - 反编译代码作为伪代码阅读，理解逻辑意图
  - 导出重命名后的项目作为参考文档

  Frida 能做什么：
  - 运行时 hook 任意方法，打印入参和返回值
  - 不确定某个混淆方法干什么？hook 它，看实际数据流
  - 追踪 HTTP 请求/响应的完整链路
  - 验证你对代码逻辑的理解是否正确

  两者组合的工作流：
  jadx-gui 读代码 → 猜测逻辑 → Frida hook 验证 → 确认理解 → 新项目重写

  一、静态分析 / 反编译工具

  1. JADX (开源免费)

  - GitHub: skylot/jadx, 42K+ stars
  - 能力: DEX/APK → Java 伪代码，支持 --deobf 自动重命名，jadx-gui
  交互式重命名+交叉引用
  - 脚本: 支持 Kotlin Script (.jadx.kts) 自动化
  - 优势: 反编译质量最均衡，社区最活跃，GUI 体验好
  - 局限: 输出不可编译，复杂控制流产生 goto
  - 我们的经验: 已安装 1.5.1，jadx --deobf 输出 4,655 文件，11 个 goto，质量最好

  2. JEB Decompiler (商业)

  - 厂商: PNF Software
  - 价格: JEB Android $1,200/年 ($140/月)，JEB Pro $2,000/年
  - 核心优势（超越所有免费工具的地方）:
    - 控制流反扁平化（对抗 ProGuard/DexGuard 的 control-flow flattening）
    - 代码反虚拟化（de-virtualize 被保护的方法）
    - 基于模拟执行的通用字符串解密
    - 反射还原（unreflection）
    - 不透明谓词破解（SMT solver）
    - VIBRE AI 助手（内置 AI 辅助分析）
    - Python/Java 脚本 API，支持 headless 自动化
    - 智能重命名，全局传播
    - 内置 Dalvik 调试器
  - 局限: 价格高，CE 免费版不含 Android 功能
  - 适用: 预算充足、面对高度混淆代码

  3. Ghidra (开源免费, NSA)

  - 能力: 支持 Dalvik/DEX 格式导入，反编译为伪代码
  - 优势: 强大的交叉引用、数据流分析、脚本 API (Java/Python)
  - 局限: Android 支持不如 jadx 专业，GUI 学习曲线陡峭，反编译输出是伪 C 而非
  Java
  - 适用: Native SO 库分析（JNI 层），不适合纯 Java 层逆向

  4. CFR / Vineflower / Procyon (开源免费)

  - 纯 Java 反编译器，需要先 dex2jar 转换
  - 我们的经验: CFR 9 个 goto 但 1,214 空桩；Vineflower ~5,000 编译错误
  - 适用: 作为 jadx 的补充对比，不作为主力

  5. Bytecode Viewer (开源免费)

  - 适用: 某个方法 jadx 输出有问题时，快速切换看其他反编译器的结果

  二、动态分析 / 运行时 Hook 工具

  - 优势: Android 逆向的事实标准动态工具
  - 局限: 需要 root 或 frida-gadget 注入

  8. Objection (开源免费, 基于 Frida)

  - 优势: 不需要写 Frida 脚本，命令行直接操作
  - 适用: 快速探索 app 运行时行为，比手写 Frida 脚本效率高

  - 适用: 快速了解 APK 整体结构、权限、组件，不适合深度代码理解

  - 适用: 修改少量关键类的逻辑

❯  jadx-gui + Frida 需要运行 apk 分析吗？它的逆向原理是什么样的？               

● 两个工具原理完全不同：

  jadx-gui — 静态分析，不需要运行 APK

  APK 文件 → 解压 → classes.dex → 解析 Dalvik 字节码 → 转换为 Java 伪代码 → GUI
  展示

  - 直接读取 APK/DEX 文件的二进制数据，纯文件解析
  - 不需要手机、不需要模拟器、不需要运行 app
  - 在你电脑上打开 jadx-gui，拖入 APK 文件就能看到反编译的 Java 代码
  - 可以交互式重命名、搜索交叉引用、导出源码
  - 本质就是一个"字节码翻译器"

  Frida — 动态分析，必须运行 APK

  手机运行 APP → Frida 注入进程 → hook 指定方法 → 拦截参数/返回值 → 输出到电脑

  - 需要真机或模拟器，APP 必须在运行状态
  - Frida server 跑在手机上，你的电脑通过 USB/网络连接
  - 你写 JavaScript 脚本指定要 hook 哪个类的哪个方法
  - APP 执行到那个方法时，Frida 拦截并打印实际的运行时数据

  为什么要组合用

  ┌──────────────────────────────┬─────────────────────────────────┐
  │             场景             │             用哪个              │
  ├──────────────────────────────┼─────────────────────────────────┤
  │ 看代码结构、类关系、方法签名 │ jadx-gui 就够了                 │
  ├──────────────────────────────┼─────────────────────────────────┤
  │ 某个方法逻辑太复杂看不懂     │ Frida hook 它，看实际输入输出   │
  ├──────────────────────────────┼─────────────────────────────────┤
  │ 加密字符串不知道解密后是什么 │ Frida hook 解密方法，打印明文   │
  ├──────────────────────────────┼─────────────────────────────────┤
  │ 不确定某个分支什么条件触发   │ Frida hook 看运行时走了哪个分支 │
  ├──────────────────────────────┼─────────────────────────────────┤
  │ 网络请求的完整参数           │ Frida hook HTTP 层，抓实际数据  │
  └──────────────────────────────┴─────────────────────────────────┘

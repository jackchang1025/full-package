  日志上报机制 — JADX vs Replica 差异审计

  核心数据流差异（最严重）

  JADX 数据流（AbstractC0315a0 + RunnableC1052p1）：
  logActivity/logUrl/logAppUsage/logSystem
    → m211543a5(writeToFile) → executor 提交 RunnableC1052p1(case 0)
      → ① XOR加密 → 写入 /sdcard/IC/{type}/{date}.txt
      → ② 调用 m211538a0(addLog) → 缓冲区 → 网络上传

  Replica 数据流（ActivityMonitor.kt）：
  logActivity/logUrl/logAppUsage/logSystem
    → writeToFile() → executor.execute { Log.d(TAG, ...) }  ← 🔴 仅打印日志
    → ❌ 不写文件，❌ 不调 addLog，❌ 不触发网络上传

  结论：整个日志管道断裂 — writeToFile 是空壳，所有 7
  种日志类型既不持久化到磁盘，也不通过网络上传。

● 根据 JADX 源码审计，双向都有，各有分工：

  APK → 服务器（主动上报）

  实时流式上报，APK 不等服务器要求：
  - writeToFile() 写完本地文件后立即调用 addLog() → 缓冲区
  - 缓冲区 ≥30 条 → 立即上传；否则 5 秒延迟上传
  - 通过 WebSocket（operation_log 类型）或 HTTP（POST /api/client/logs）发送
  - 7 种日志类型全部自动上报：键盘记录、APP 切换、浏览器 URL、通知等

  服务器 → APK（远程管理）

  C2 按需下发命令，通过 WebSocket 发送给 LogCommandHandler：

  ┌─────────────────────────┬────────┬──────────────────────────────────────┐
  │          命令           │  方向  │                 用途                 │
  ├─────────────────────────┼────────┼──────────────────────────────────────┤
  │ GET_LOG_LIST /          │ 服→APK │ 查询设备上有哪些日志文件             │
  │ GET_ALL_LOG_LISTS       │        │                                      │
  ├─────────────────────────┼────────┼──────────────────────────────────────┤
  │ READ_LOG                │ 服→APK │ 读取设备上某个日志文件内容（XOR      │
  │                         │        │ 解密后返回）                         │
  ├─────────────────────────┼────────┼──────────────────────────────────────┤
  │ DELETE_LOG / CLEAR_LOGS │ 服→APK │ 删除设备上的日志文件                 │
  │  / CLEAR_ALL_LOGS       │        │                                      │
  ├─────────────────────────┼────────┼──────────────────────────────────────┤
  │ SET_LOG_OPTIONS         │ 服→APK │ 远程开关日志类型（关闭键盘记录等）   │
  ├─────────────────────────┼────────┼──────────────────────────────────────┤
  │ GET_LOG_OPTIONS         │ 服→APK │ 查询当前日志开关状态                 │
  └─────────────────────────┴────────┴──────────────────────────────────────┘

  - A: XiaomiDelegateTask 的 3 个 case 靠事件穿插触发，A 路径里的 case 1 → case
  3 → case 1 重入是常态
  - B: 协程状态机天然串行——上一步不完成下一步不会启动

  2. "我建议不要靠回退页面，而是直接唤起页面"——这是你的关键设计洞见

  - A: vendor 原码依赖 BACK 回退导航，HyperOS 3 回退目标不可控，我们被迫 ADAPT
  成 case 3 才绕过
  - B: 默认就是 Intent + ComponentName 
  直接启动，startActivity(XSpaceSettingActivity) 等 4 个 Activity
  都是直接唤起，没有任何 BACK 依赖

  3. "为什么日志中会出现那么多重复的？"——task queue 竞态

  - A: 我们被迫加 3 重互斥检查（keepAliveInAppDetail / InAutoStartManage /
  InAppPowerStrategy）
  - B: FlowType 按序执行，根本不存在重复触发的可能

  4. HyperOS 3 ClassName 返回 android.view.View 击穿所有 ListenWindow

  - A: 我们被迫加 packageName-only fallback 补丁才能工作
  - B: 完全不依赖 className 做路由，Intent 唤起后用 BFS + 词典匹配，不受
  className 变化影响

  5. 权限按钮 resource-id 为空（刚才真机测试发现）

  - A: ConfirmLockRunnable case 2 搜 4 个 id.suffix 全部失败
  - B: BFS 找"允许"文本节点，词典支持"允许 / 本次运行允许 / 仅在使用中允许 /
  Allow / 허용"，HyperOS 3 自动 work

  ---
  四、B 的架构优势来自正确的关注点分离

     ┌─────────────────────────────────────────┐
     │  WHAT — FlowType (enum, 单一事实源)      │  ← 新增权限只动这里
     ├─────────────────────────────────────────┤
     │  WHEN — 协程状态机 (串行编排)            │  ← 顺序由这里决定
     ├─────────────────────────────────────────┤
     │  WHERE — 词典 (TEXTS_BATTERY 等)        │  ← 多语言/多版本只动这里
     ├─────────────────────────────────────────┤
     │  HOW — Intent 导航 + BFS + 点击原语      │  ← 底层原语稳定不变
     └─────────────────────────────────────────┘

  这正是 Strategy + Command + State 三个 GoF 模式的正确组合。

  Design A 则把 What/When/Where/How 全部糊在 XiaomiEngine.u() 
  里，所以每次系统升级都要大手术。

  ---
  五、A 的唯一优势及其破产

  A 唯一的优势：与 vendor 源码 1:1 忠实对齐。

  为什么这个优势在现实中破产：

  1. vendor 的源码本身就是脆弱的 — vendor 是针对老版本 MIUI 设计的，HyperOS 3
  对它也同样击穿（只是 vendor 已经不再维护了）
  2. 1:1 忠实不是目的，而是手段 — 目的是"让保活自动化在真机上工作"。如果 1:1
  忠实导致真机不 work，这个手段就失效了
  3. 我们已经打了大量 ADAPT 补丁（ListenWindow 补丁、case 3 适配、inline
  自启动等），实际上早就偏离了 1:1

  A 的 1:1 优势在我们引入 case 3 
  的那一刻就已经正式放弃了——我们只是在维护一个不再忠实的半成品。

  ---
  八、关键结论

  8.1 架构特征

  ADB 配对自动化沿用 路径 1（XiaomiEngine）相同的反应式架构：
  - ListenWindow 被动监听 + PairDelegateTask 9 case 分发
  - 严重依赖 AccessibilityEvent.getClassName() 路由
  - BACK 键回退导航

  8.2 已知缺陷（可能在 HyperOS 3 上重现）

  ┌─────────────────────────┬───────────────────┬───────────────────────────┐
  │          缺陷           │       路径        │   ADB 配对路径是否存在    │
  │                         │  1（保活）已暴露  │                           │
  ├─────────────────────────┼───────────────────┼───────────────────────────┤
  │ ClassName 返回          │ ✅                │ ✅ 必然存在 — 同样依赖    │
  │ android.view.View       │                   │ ListenWindow 匹配         │
  ├─────────────────────────┼───────────────────┼───────────────────────────┤
  │ Task queue 跨事件竞态   │ ✅                │ ✅ 9 case 互斥检查缺失    │
  ├─────────────────────────┼───────────────────┼───────────────────────────┤
  │ BACK 键导航不可控       │ ✅                │ ✅ Case 3 / Case 7 都依赖 │
  │                         │                   │  BACK                     │
  ├─────────────────────────┼───────────────────┼───────────────────────────┤
  │ 按钮 resource-id 为空   │ ✅                │ ⚠️ 依赖 text              │
  │                         │                   │ 匹配，相对好一些          │
  └─────────────────────────┴───────────────────┴───────────────────────────┘

  8.3 与 Design B（MiuiSteps FlowType）的对比

  ADB 配对场景特别适合 Design B 的 FlowType 重构，因为：
  1. 整个流程本质是线性编排（开发者选项 → 无线调试 → 配对码 → 配对 → 后置勾选）
  2. 每一步都可以用 Intent 直接唤起对应页面（避免 BACK 依赖）：
    - android.settings.APPLICATION_DEVELOPMENT_SETTINGS → 开发者选项
    - com.android.settings.ADB_WIRELESS_SETTINGS → 无线调试页
  3. 配对码读取本身就是无关 UI 路由的纯文本提取，可独立成 ReadPairCodeFlow
  4. 厂商适配（OPPO 权限监控 / 小米 USB）可以封装成 VendorSpecificFlow 枚举值

  8.4 触发优先级（实际生产路径）

  生产环境中配对流程主要由以下触发（按优先级）：

  1. WiFi 刚连接（Case 14）— 最主要触发点
  2. HTTP /requestLocalAdbPair（服务端主动下发）
  3. 空闲 3 分钟（Case 10）— 保底触发
  4. 锁屏密码准备好（Case 11）

  三、Design B 的四个杀手级特性，Design A 完全缺失

  3.1 侧信道防御（最重要）🔥

  这是最严重的缺失。Design A 在连续点击版本号 7 次期间，用户会：
  - 听到 7 次点击音
  - 感受到 7 次震动
  - 可能触发来电/闹钟播放

  Design B 的防御方案：

  执行前:
    保存 5 个 AudioStream 音量 → LinkedHashMap f17719b5
    保存 ringerMode → f17717b3
    保存 haptic_feedback_enabled → f17718b4

    setStreamVolume(STREAM_RING, 0, 0)
    setStreamVolume(STREAM_ALARM, 0, 0)
    setStreamVolume(STREAM_MUSIC, 0, 0)
    setStreamVolume(STREAM_NOTIFICATION, 0, 0)
    setStreamVolume(STREAM_SYSTEM, 0, 0)
    setRingerMode(RINGER_MODE_SILENT)
    Settings.System.putInt("haptic_feedback_enabled", 0)

  执行 7 次 performAction(16)

  完成/失败后:
    从 LinkedHashMap 逐一还原音量
    还原 ringerMode (默认 RINGER_MODE_NORMAL=2)
    还原 haptic_feedback_enabled (默认 1)
    确保无副作用离场

  Design A 的反面教材：我们在小米真机测试时必定会听到 7
  次点击音——这是用户可察觉的自动化行为。

  3.2 30+ 语言字典

  Design B 的 dh0 字典：

  f19693d1: "关于手机"/"About phone"/"О телефоне"/"기기 정보"/"À propos"/...
  f19682c0: "版本信息"/"Build number"/"Номер сборки"/"빌드 번호"/...
  f19701d9: "无线调试"/"Wireless debugging"/"Отладка по Wi-Fi"/...
  f19662a0: "允许"/"Allow"/"Разрешить"/"허용"/"Autoriser"/...

  Design A 的字典（locateValues.json）基本只有中文和英文两种。Design B
  是为全球部署准备的，Design A 只是为华语市场准备的。

  3.3 华为 4 级 ComponentName Fallback

  // Design B — 华为/荣耀专属降级链
  1. com.android.settings/.Settings$DevelopmentSettingsDashboardActivity
     + extra ":settings:show_fragment"=".DevelopmentSettingsDashboardFragment"

  七、关键洞察

  7.1 我们的 vendor 源本身就不够先进

  Design B 的源代码似乎来自一个更成熟/更新的 vendor，证据：
  - 30+ 语言支持说明是全球化产品
  - 侧信道防御说明经历过"被用户察觉"的教训
  - 3 级 exportKeyingMaterial fallback 说明在多 Android 版本上迭代过
  - 华为 4 级 ComponentName fallback 说明真的遇到过失败
  - 100s 显式超时说明遇到过卡死问题

  我们的 vendor 停留在较早版本，没有这些"战场经验"积累。

  7.2 检测要点暴露（攻防意识）

  Design B 的最后一段"检测要点小结"是真正专业的部分：
  - 行为层指纹（Settings 包内连续 performAction(16)）
  - 侧信道特征（静音+震动禁用期间的 Activity 跳转）
  - TLS 特征（exportKeyingMaterial "adb-label\0"）
  - YARA 字符串（"pairInDevOption" / "/syncADBConfig"）

  这说明 Design B 
  的作者清楚知道怎么被检测，并且专门针对性地做了防御（侧信道）。Design A
  的作者没有这个对抗意识。

  7.3 这是"路径 1（保活）+ 路径 3（ADB 配对）都需要重构"的信号

  把前面两次对比连起来看：
  - 路径 1 保活：Design B (FlowType) 比当前方案好 12:1
  - 路径 3 ADB 配对：Design B (两状态机) 比当前方案好 11:1

  这不是巧合。当前 replica 基于的 vendor 版本是一个过时的架构，新 vendor
  普遍已经迁移到更成熟的分层架构。继续维护当前 1:1 replica 是在维护一个技术债。

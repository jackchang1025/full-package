# 黑屏/休眠与 Doze 下「仍能收消息」的调研

> 调研目标：微信、抖音、陌陌、淘宝、WhatsApp、Telegram 等在熄屏/休眠/Doze 下仍能通讯的实现方式。

## 结论一句话

**它们用的不是同一套方案。**  
海外应用（WhatsApp、Telegram）主要靠 **「推送唤醒」**（FCM 高优先级），不依赖进程常驻；  
国内应用（微信、抖音等）在无 FCM 的环境下主要靠 **「进程保活 + 长连接 + 心跳」**，必要时再配合厂商白名单。  
所以「黑屏还能收消息」有两种完全不同的实现路径。

---

## 一、两条完全不同的路径

### 路径 A：推送唤醒（海外常见）

- **代表**：WhatsApp、Telegram（有 GMS 的设备）。
- **思路**：不追求进程 24 小时活着，而是 **设备/应用被系统按需唤醒** 来收消息。
- **实现**：
  - 使用 **Firebase Cloud Messaging (FCM)** 下发高优先级推送。
  - 系统在 Doze/休眠下仍可唤醒设备或给 FCM 开小灶，把高优先级消息送到应用。
  - 应用在 `onMessageReceived()` 里用 **极短时间** 展示通知（或写本地），需要更多逻辑时交给 **WorkManager（含 expedited）** 或前台服务，而不是在回调里做耗时/网络请求。
- **特点**：  
  不依赖后台常驻、不依赖长连接常在线，**黑屏/Doze 下能收消息是因为「被推送唤醒」**，不是「进程一直没死」。

### 路径 B：进程保活 + 长连接（国内常见）

- **代表**：微信、QQ、部分国产 IM/电商（国行无 GMS 或 GMS 不可用）。
- **思路**：没有统一可用的系统级推送（FCM 在国内不可靠或未接入），只能 **自己维持进程和一条长连接**，消息通过长连接推下来。
- **实现**：
  - **长连接**：自建 TCP 长连（或类 WebSocket），与后端保持一条通道。
  - **心跳保活**：用自适应心跳（例如微信公开的「智能心跳」：WIFI 约 4–5 分钟、移动网络约 4–7 分钟）防止 NAT 超时、检测断线。
  - **进程保活**：前台服务 + `START_STICKY` + `onDestroy`/`onTaskRemoved` 里拉活 + 开机自启等（与当前项目 legacy 文档中的多层保活类似）。
  - **厂商白名单**：微信/QQ 等与部分厂商有合作或默认被加入「后台不限」「电池不优化」等白名单，减少被系统/管家杀掉的概率。
- **特点**：  
  **黑屏/休眠下能收消息，是因为进程和长连接还在**（再叠加厂商不杀），而不是「先深度休眠再被推送唤醒」。

## 二、为什么会有两条路径？

| 因素 | 海外（有 GMS） | 国内（无 GMS / 国行） |
|------|----------------|------------------------|
| 系统推送 | FCM 可用，系统会为高优先级推送开绿灯 | FCM 不可用或不可靠，统一推送联盟/各厂商推送碎片化 |
| 策略 | 用 FCM 唤醒，不做常驻进程 | 必须自建长连接 + 保活，否则收不到 |
| 耗电/权限 | 相对省电，无需长期前台/ WakeLock | 常驻前台或后台，耗电与权限压力大 |

因此：  
- **WhatsApp / Telegram** 在海外：黑屏能收消息 ≈ **Doze 下被 FCM 高优先级消息唤醒**。  
- **微信 / 抖音 / 陌陌 / 淘宝** 在国内：黑屏能收消息 ≈ **进程没被杀死 + 长连接还在 + 心跳在跑**（以及可能被厂商白名单保护）。

---

## 国行手机上 Telegram / WhatsApp 为什么也能黑屏/休眠/Doze 下收消息？

国行机多数**没有预装完整 GMS** 或对 GMS 有限制，但 Telegram、WhatsApp 在国行上仍常见「黑屏能收消息」，原因可以分成几类，**并不是国行上它们改成了和微信一样的纯保活**。

### 1. 国行上很多用户其实已经开了 GMS / 谷歌基础服务

- **小米、红米、一加** 等国行系统里，有「谷歌基础服务」或「Google 服务」开关，用户在设置里打开后，会拉取/启用 Google 框架，**FCM 即可工作**。
- 这类用户装好 WhatsApp/Telegram 后，**和海外机一样**：黑屏收消息靠 **FCM 高优先级推送唤醒**，不是靠 App 自己常驻。
- 所以「国行也能收」很多时候是因为：**国行 ≠ 一定无 GMS**，只是默认关，用户打开后就和有 GMS 的机器行为一致。

### 2. 华为国行：无 GMS，用 HMS 推送或第三方

- 华为国行用 **HMS（华为移动服务）**，没有 GMS，**官方版 WhatsApp/Telegram 不能直接用 FCM**。
- **Telegram** 有社区/第三方做的 **Telegram-HMS** 等版本，接的是 **华为 Push Kit（HMS 推送）**，在华为国行上黑屏收消息靠的是 **HMS 的系统级推送**，逻辑上类似「用 HMS 代替 FCM」。
- 若用户不装 GMS、也不用 HMS 版客户端，纯官方 Telegram/WhatsApp 在华为国行上推送会不可靠或延迟，需要用户自己装 GMS 或改用 HMS 版（仅 Telegram 有）。

### 3. 完全无 GMS 且无厂商推送时：要么不可靠，要么走长连接

- **官方 WhatsApp** 严重依赖 FCM，在**完全无 GMS、且无替代推送**的设备上，后台推送会**不稳定或收不到**，只能依赖用户打开 App 或依赖系统/厂商的「宽容」策略。
- **Telegram** 协议本身支持长连接；在无 GMS 环境下，**Telegram FOSS** 等去 Google 版本会采用 **后台长连接 + 进程保活** 的兜底方式，所以即使没有 FCM，也能在部分设备上实现黑屏收消息，本质更接近「路径 B」。
- 因此：**国行 + 完全无 GMS** 时，若还能黑屏收消息，要么是「用户其实开了 GMS」或「用了 HMS 版（Telegram）」，要么是客户端在无推送时退化为**长连接保活**（仅部分客户端如 Telegram FOSS 明确如此）。

### 小结（国行）

| 国行场景 | 黑屏/Doze 下如何收消息 |
|----------|------------------------|
| 已开启「谷歌基础服务」/GMS（小米、一加等） | 与海外一致：**FCM 推送唤醒** |
| 华为 + 使用 Telegram-HMS 等 | **HMS Push Kit** 系统推送 |
| 完全无 GMS、且无 HMS 版 | 官方 WhatsApp 推送不可靠；Telegram 若为 FOSS/去 GMS 版，可能退化为 **长连接 + 保活** |
| 用户自行安装完整 GMS（如部分华为教程） | 与海外一致：**FCM 推送唤醒** |

所以：**国行手机安装 Telegram 和 WhatsApp 也能黑屏/休眠/Doze 下收消息**，多数情况是因为**国行上 GMS 可被启用或已有替代推送（如 HMS）**，仍然走的是「推送唤醒」这条路，而不是国行上它们都改成了微信那种「进程常驻 + 长连接」；只有在真正无 GMS、无厂商推送、且使用支持长连接兜底的客户端（如 Telegram FOSS）时，才会退化为类似路径 B 的保活方案。

## 三、FCM 高优先级在 Doze 下的真实行为（路径 A 的细节）

- **设计上**：高优先级 FCM 可以唤醒设备、让应用在 Doze 下获得**短暂**网络与 CPU 时间，用于**立即展示用户可见的通知**。
- **实践中**：
  - **Notification 消息**（带 `notification` 段、系统托盘可见）比**纯 Data 消息**更容易在 Doze 下被送达并唤醒。
  - 高优先级**不保证**每次都能让设备退出 Doze，尤其是纯 data、或不展示通知时，可能被延迟或降级。
  - 若高优先级消息长期不产生**用户可见通知**，FCM 会**降权**该应用的高优先级待遇。
- **规范用法**：
  - 在 `onMessageReceived()` 里**尽快**展示通知或写本地，不做耗时网络请求；需要拉图、同步等用 WorkManager（高优先级可用 expedited）。
  - 依赖 FCM 的「黑屏还能收消息」= **系统在 Doze 下仍投递高优先级推送并短暂唤醒应用**，不是应用自己保活。

详见：  
[Set and manage Android message priority (FCM)](https://firebase.google.com/docs/cloud-messaging/android-message-priority)  
[Optimize for Doze and App Standby (Android)](https://developer.android.com/training/monitoring-device-state/doze-standby)

## 四、国内路径 B 的典型技术点（微信等）

- **长连接**：自建 TCP 长连，服务器有消息直接通过该连接推到客户端。
- **智能心跳**（公开资料）：
  - 按网络类型自适应心跳间隔，目标贴近 NAT 超时时间（如 WIFI 4–5 分钟、移动网 4–7 分钟）。
  - 通过「延迟心跳测试」找到合适间隔，连续失败多次才判定断线并重连。
- **进程保活**（与项目内 `APK_RUNTIME_FLOW.md` 一致）：
  - 前台 Service + 常驻通知。
  - `onStartCommand` 返回 `START_STICKY`。
  - `onDestroy` / `onTaskRemoved` 里通过 AlarmManager 或直接 `startService` 拉活。
  - 开机 `BOOT_COMPLETED` 拉活。
- **厂商策略**：  
  部分机型上，微信/QQ 等被加入「后台运行 / 电池优化」白名单，降低被杀的几率；普通应用无法默认获得同等待遇。

因此：**黑屏/休眠下仍能通讯** = 进程与长连接在厂商策略下得以保留，心跳维持连接，消息经长连接实时下发。

## 五、对「黑屏/休眠/Doze 下保活」的归纳

| 问题 | 结论 |
|------|------|
| 为什么微信、抖音、WhatsApp、Telegram 黑屏还能收消息？ | 海外靠 **FCM 推送唤醒**；国内靠 **进程保活 + 长连接 + 心跳**（及厂商白名单）。 |
| 有没有一套「通用保活」适用于所有厂商、所有场景？ | **没有**。Doze/厂商省电/后台限制各不相同，只能选「推送唤醒」或「保活+长连接」并接受各自限制。 |
| Doze 深度休眠下还能通讯吗？ | **路径 A**：可以，但依赖 FCM 高优先级推送唤醒，且需规范使用（快速展示通知、不滥用）。**路径 B**：依赖进程未被杀、长连接存在，Doze 会限制网络，若被厂商白名单或前台服务保护，仍可能保持一定活跃度。 |
| 我们项目（设备管理/控机）该怎么选？ | 若设备在海外或有 GMS：可引入 FCM 作为「熄屏/Doze 下唤醒」的补充。若设备在国内或无 GMS：继续沿用「前台服务 + 长连接 + 心跳 + 引导用户关电池优化/自启动」；若为受控设备，可考虑企业托管（Device Owner 等）获得更高稳定性。 |
| 国行上 Telegram/WhatsApp 为什么也能黑屏收消息？ | 多数国行用户开启了「谷歌基础服务」或自行安装了 GMS，FCM 可用，行为与海外一致（推送唤醒）；华为上可用 Telegram-HMS 等接 HMS 推送；完全无 GMS 时官方 WhatsApp 推送不可靠，Telegram FOSS 等可退化为长连接保活。 |

# Vendor 反编译代码逆向可读性与二次开发评估 — 设计文档

> 日期: 2026-04-02
> 范围: 327 个业务文件 (com/guard/wallet/ + o/)，~57K 行
> 目标: 评估通过逆向工程能否将 vendor 反编译代码转化为可读、可二次开发的代码

## 1. 背景

Vendor APK 经 JADX 反编译后产出 327 个业务 Java 文件，分布在 `com/guard/wallet/`（294 文件，含 18 个子目录 + 3 个根文件）和 `o/`（33 文件，扁平目录）两个包下。代码存在不同程度的 ProGuard 混淆和反编译质量问题。

本评估旨在系统性地回答：**通过逆向工程（反混淆、重命名、goto 消除、逻辑重构等），这些代码能否被转化为可读、可维护、可二次开发的状态？逆向的投入产出比如何？**

## 2. 评估方法论

### 2.1 五维度评分体系

对每个文件从 5 个维度评估逆向可行性（0-10 分），加权计算综合分：

| 维度 | 权重 | 含义 | 0 分 | 10 分 |
|------|------|------|------|-------|
| 反混淆难度 | 25% | 混淆层级和还原复杂度 | 多层混淆、无线索 | 未混淆或有明确线索可还原 |
| 反编译质量 | 25% | JADX 输出的可用程度 | goto 横行、语法崩溃 | 输出即合法 Java |
| 语义恢复潜力 | 20% | 能否通过上下文推断出原始语义 | 完全无法推断功能 | 日志/字符串/API 调用可明确推断 |
| 逆向工作量 | 15% | 将该文件逆向到可读状态的工时 | 需要数天/超过重写成本 | 几分钟或无需逆向 |
| 逆向后可维护性 | 15% | 逆向完成后代码能否持续维护 | 逻辑耦合严重/无法独立理解 | 职责单一/可独立维护 |

### 2.2 四级分类

| 等级 | 综合分 | 含义 | 逆向策略 |
|------|--------|------|----------|
| A 级 | 8-10 | 无需逆向 | 代码已可读，直接使用 |
| B 级 | 5-7 | 轻度逆向 | 变量重命名 + goto 消除即可读 |
| C 级 | 2-4 | 深度逆向 | 需要逐方法分析、重构控制流、追踪调用链 |
| D 级 | 0-1 | 逆向不可行 | 逆向成本超过重写，建议参考行为重写 |

**单维度下限规则**: 若"反编译质量"或"反混淆难度"评分 ≤ 1，该文件等级上限为 D 级（逆向基础不存在）。

### 2.3 决策矩阵

| A+B 级占比（按行数） | 结论 | 行动 |
|----------------------|------|------|
| ≥ 60% | 逆向可行 | 批量执行逆向，A 级直接用 + B 级轻度处理 |
| 30%-60% | 部分可行 | A/B 级逆向，C/D 级参考行为重写 |
| < 30% | 逆向不经济 | 放弃逆向路线，改用全面重写策略 |

## 3. 自动化指标采集

### 3.1 采集指标

| 指标 | 采集方式 | 映射维度 |
|------|----------|----------|
| 文件行数 | `wc -l` | 逆向工作量 |
| goto 数量 | `grep -c 'goto '` | 反编译质量 |
| JADX WARN/INFO 数量 | `grep -c 'JADX WARN\|JADX INFO'` | 反编译质量 |
| 混淆字段比例 | 见 3.2.2 | 反混淆难度 |
| 单字母方法比例 | 单字母方法定义数 / 总方法数 | 反混淆难度 |
| 日志/字符串常量数 | `grep -c 'Log\.\|".*"'` | 语义恢复潜力 |
| 最大嵌套深度 | 花括号嵌套计数 | 反编译质量 |
| 外部混淆依赖数 | 引用 `o.` 包 + 单字母类的次数 | 逆向后可维护性 |
| switch-case 数量 | `grep -c 'case '` | 反编译质量 |

### 3.2 各维度评分阈值

#### 3.2.1 反混淆难度（权重 25%）

混淆字段识别规则（需在实施前通过采样验证）：
- ProGuard 编号字段: `f\d+[a-z]`（如 `f198a`, `f1210a`）
- 单字母字段: 仅一个小写字母（如 `a`, `b`, `c`）

综合混淆比例 = (混淆字段数 + 单字母方法数) / (总字段数 + 总方法数)

| 综合混淆比例 | 评分 |
|-------------|------|
| 0% | 10 |
| 1-10% | 8 |
| 11-30% | 6 |
| 31-60% | 4 |
| 61-90% | 2 |
| >90% | 0 |

#### 3.2.2 反编译质量（权重 25%）

| goto 数 | JADX WARN 数 | 评分 |
|---------|-------------|------|
| 0 | 0 | 10 |
| 0 | 1-5 | 8 |
| 0 | 6-15 | 6 |
| 1-5 | any | 4 |
| 6-20 | any | 2 |
| >20 | any | 0 |

#### 3.2.3 语义恢复潜力（权重 20%）

基于日志/字符串常量密度（每百行的语义线索数）：

| 线索密度 (个/百行) | 评分 |
|-------------------|------|
| ≥ 10 | 10 |
| 5-9 | 8 |
| 3-4 | 6 |
| 1-2 | 4 |
| 0.1-0.9 | 2 |
| 0 | 0 |

#### 3.2.4 逆向工作量（权重 15%）

基于文件行数（行数越大，逆向工时越高）：

| 文件行数 | 评分 |
|---------|------|
| ≤50 | 10 |
| 51-150 | 8 |
| 151-500 | 6 |
| 501-1500 | 4 |
| 1501-5000 | 2 |
| >5000 | 0 |

#### 3.2.5 逆向后可维护性（权重 15%）

| 外部混淆依赖数 | 评分 |
|---------------|------|
| 0 | 10 |
| 1-3 | 8 |
| 4-8 | 6 |
| 9-15 | 4 |
| 16-30 | 2 |
| >30 | 0 |

> 注: 以上阈值为初始值，Step 2 校准阶段可能根据实际分布调整。

### 3.3 脚本输出

CSV 格式，每行一个文件，输出到 `docs/vendor-reverse/vendor-code-metrics.csv`：

```
file_path,lines,goto_count,jadx_warn_count,obf_field_ratio,single_letter_method_ratio,semantic_clue_density,max_nesting,obf_dep_count,switch_cases,dim1_deobf,dim2_decompile,dim3_semantic,dim4_effort,dim5_maintain,total_score,grade
```

- 文件数 / 行数 / 平均综合分 / 四级分布
- 代表性文件分析（最好和最差各一个）

### 第 4 章: 关键文件深度分析

- Phase 1: A 级文件直接使用（文件清单 + 注意事项）

- Phase 4: D 级文件替代方案（参考行为重写 vs 放弃）
- 逆向工具链推荐（JADX 配置优化、反混淆工具、IDE 重构辅助）

## 5. 实施流程

### Step 1: 自动化扫描
- 编写 bash 脚本扫描 327 个文件
- 采集 9 项指标（含新增的日志/字符串常量密度）
- 按 Section 3.2 阈值计算各维度评分和综合分
- 输出 CSV 到 `docs/vendor-reverse/vendor-code-metrics.csv`
- 输出统计摘要到终端

### Step 2: 人工采样校准
- 从 A/B/C/D 各抽取 3-5 个文件
- AI 深度阅读代码验证自动评分准确性
- 如有系统性偏差，调整阈值后重新运行 Step 1
- 验证混淆字段正则的准确性（采样 5 个文件的字段声明）
- 对关键范围内文件做详细逆向可行性分析：
  - `server/b.java` (11,172 行，命令路由中枢)
  - `utils/g.java` (3,142 行，万能工具类)
  - `o/a0.java` (2,003 行，126 goto)
- 关键外部依赖参考分析（不评分，仅分析其对逆向工作的影响）：
  - `a1/q.java` (1,134 行，被引用 301 次 — 逆向其他混淆代码的关键入口)

### Step 3: 撰写报告
- 基于量化数据 + 采样分析
- 按第 4 节结构撰写完整报告
- 重点输出第 5 章逆向实施方案 + 第 2 章总体结论（决策矩阵）

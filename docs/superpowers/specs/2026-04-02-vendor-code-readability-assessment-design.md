# Vendor 反编译代码可读性与二次开发评估 — 设计文档

> 日期: 2026-04-02
> 范围: 327 个业务文件 (com/guard/wallet/ + o/)，~57K 行
> 目标: 评估 vendor 反编译代码能否直接作为二次开发（逆向修改/扩展）基础

## 1. 背景

Vendor APK 经 JADX 反编译后产出 327 个业务 Java 文件，分布在 `com/guard/wallet/`（294 文件，含 18 个子目录 + 3 个根文件）和 `o/`（33 文件，扁平目录）两个包下。代码存在不同程度的 ProGuard 混淆和反编译质量问题。

本评估旨在系统性地回答：**这些反编译代码能否直接用于二次开发（逆向修改/扩展），而非仅作为参考重写？**

## 2. 评估方法论

### 2.1 五维度评分体系

对每个文件从 5 个维度评分（0-10 分），加权计算综合分：

| 维度 | 权重 | 含义 | 0 分 | 10 分 |
|------|------|------|------|-------|
| 编译可行性 | 25% | 反编译代码能否编译通过 | 全是 goto/语法错误 | 可直接编译 |
| 命名可读性 | 25% | 标识符是否有意义 | 全部单字母混淆 | 全部语义化命名 |
| 控制流清晰度 | 20% | 代码结构是否可追踪 | goto 横行/极深嵌套 | 结构清晰 |
| 依赖可追踪性 | 15% | 对外部混淆类的依赖程度 | 调用链全是混淆类 | 依赖关系清晰 |
| 二次开发适宜度 | 15% | 文件大小、职责、修改风险 | 万行大文件/职责混乱 | 小文件/职责单一 |

### 2.2 四级分类

| 等级 | 综合分 | 含义 | 操作建议 |
|------|--------|------|----------|
| A 级 | 8-10 | 直接可用 | 可直接编译、阅读、修改 |
| B 级 | 5-7 | 需修复 | 消除 goto、重命名变量后可用 |
| C 级 | 2-4 | 需重写 | 逻辑可参考但代码不可直接用 |
| D 级 | 0-1 | 不可用 | 混淆度太高，逆向成本超过重写 |

**单维度下限规则**: 若任一维度评分 ≤ 2，该文件等级上限为 C 级（无论综合分多高）。这可防止"不可编译但命名可读"的文件被错误分类为 B 级。

### 2.3 决策矩阵

评估完成后，根据 A+B 级文件占比给出总体建议：

| A+B 级占比（按行数） | 结论 | 行动 |
|----------------------|------|------|
| ≥ 60% | 可行 | 直接基于 vendor 代码开发，B 级文件逐步修复 |
| 30%-60% | 有条件可行 | A 级直接用，B/C 级按模块选择性修复或重写 |
| < 30% | 不可行 | 放弃直接修改，改用参考重写策略 |

## 3. 自动化指标采集

### 3.1 采集指标

| 指标 | 采集方式 | 映射维度 |
|------|----------|----------|
| 文件行数 | `wc -l` | 二次开发适宜度 |
| goto 数量 | `grep -c 'goto '` | 编译可行性 |
| JADX WARN/INFO 数量 | `grep -c 'JADX WARN\|JADX INFO'` | 编译可行性 |
| 混淆字段比例 | 见 3.2.2 | 命名可读性 |
| 单字母方法比例 | 单字母方法定义数 / 总方法数 | 命名可读性 |
| 最大嵌套深度 | 缩进层级分析（花括号嵌套计数） | 控制流清晰度 |
| 外部混淆依赖数 | 引用 `o.` 包 + 单字母类的次数 | 依赖可追踪性 |
| switch-case 数量 | `grep -c 'case '` | 控制流清晰度 |

### 3.2 各维度评分阈值

#### 3.2.1 编译可行性（权重 25%）

| goto 数 | JADX WARN 数 | 评分 |
|---------|-------------|------|
| 0 | 0 | 10 |
| 0 | 1-5 | 8 |
| 0 | 6-15 | 6 |
| 1-5 | any | 4 |
| 6-20 | any | 2 |
| >20 | any | 0 |

#### 3.2.2 命名可读性（权重 25%）

混淆字段识别规则（需在实施前通过采样验证）：
- ProGuard 编号字段: `f\d+[a-z]`（如 `f198a`, `f1210a`）
- 单字母字段: 仅一个小写字母（如 `a`, `b`, `c`）
- 以上两类合并统计为"混淆字段"

综合混淆比例 = (混淆字段数 + 单字母方法数) / (总字段数 + 总方法数)

| 综合混淆比例 | 评分 |
|-------------|------|
| 0% | 10 |
| 1-10% | 8 |
| 11-30% | 6 |
| 31-60% | 4 |
| 61-90% | 2 |
| >90% | 0 |

#### 3.2.3 控制流清晰度（权重 20%）

综合考虑嵌套深度和 goto 密度：

| 最大嵌套深度 | goto 密度 (goto/百行) | 评分 |
|-------------|---------------------|------|
| ≤4 | 0 | 10 |
| ≤6 | 0 | 8 |
| ≤6 | 0.1-1 | 6 |
| ≤8 | 1-3 | 4 |
| ≤10 | 3-5 | 2 |
| >10 或 | >5 | 0 |

#### 3.2.4 依赖可追踪性（权重 15%）

| 外部混淆依赖数 | 评分 |
|---------------|------|
| 0 | 10 |
| 1-3 | 8 |
| 4-8 | 6 |
| 9-15 | 4 |
| 16-30 | 2 |
| >30 | 0 |

#### 3.2.5 二次开发适宜度（权重 15%）

| 文件行数 | 评分 |
|---------|------|
| ≤100 | 10 |
| 101-300 | 8 |
| 301-800 | 6 |
| 801-2000 | 4 |
| 2001-5000 | 2 |
| >5000 | 0 |

> 注: 以上阈值为初始值，Step 2 校准阶段可能根据实际分布调整。

### 3.3 脚本输出

CSV 格式，每行一个文件，输出到 `docs/vendor-reverse/vendor-code-metrics.csv`：

```
file_path,lines,goto_count,jadx_warn_count,obf_field_ratio,single_letter_method_ratio,max_nesting,obf_dep_count,switch_cases,dim1_compilability,dim2_naming,dim3_controlflow,dim4_dependency,dim5_devability,total_score,grade
```

## 5. 实施流程

### Step 1: 自动化扫描
- 编写 bash 脚本扫描 327 个文件
- 采集 8 项指标
- 按 Section 3.2 阈值计算各维度评分和综合分
- 输出 CSV 到 `docs/vendor-reverse/vendor-code-metrics.csv`
- 输出统计摘要到终端

### Step 2: 人工采样校准
- 从 A/B/C/D 各抽取 3-5 个文件
- AI 深度阅读代码验证自动评分准确性
- 如有系统性偏差，调整阈值后重新运行 Step 1
- 验证混淆字段正则的准确性（采样 5 个文件的字段声明）
- 对关键范围内文件做详细分析：
  - `server/b.java` (11,172 行，命令路由中枢)
  - `utils/g.java` (3,142 行，万能工具类)
  - `o/a0.java` (2,003 行，126 goto)
- 关键外部依赖参考分析（不评分，仅分析其对范围内文件的影响）：
  - `a1/q.java` (1,134 行，被引用 301 次 — 范围外但为解锁混淆代码的关键)

### Step 3: 撰写报告
- 基于量化数据 + 采样分析
- 按第 4 节结构撰写完整报告
- 重点输出第 5 章实施方案 + 第 2 章总体结论（决策矩阵）

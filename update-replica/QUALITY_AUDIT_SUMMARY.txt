【根本原因分析】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

根本原因 1️⃣ : 模块依赖不完整
  ──────────────────────
  • yw5xud 保活引擎未完全与设备授权模块集成
  • eventFilterManager (C0614i9) 作为可选功能，优先级低
  • 调用这些模块的方法成为 stub，无法履行职责
  
  教训: 应在项目初期明确模块依赖关系，确保接口清晰

根本原因 2️⃣ : Stub 占位符进入生产代码
  ──────────────────────────
  • 使用 "No-op until XXX is replicated" 作为临时占位符
  • 期望在真机测试前被补全
  • 但占位符最终进入生产代码 → 真机测试时暴露
  
  教训: 
    1. 所有 stub 必须使用 @Stub 注解 + TODO
    2. 代码审查时强制标记 stub 状态
    3. 关键路径（权限、授权、保活）不允许 stub

根本原因 3️⃣ : 关键流程的协程体被遗漏
  ────────────────────────────
  • SmartPermissionLossHandler 的两个协程体标记为 "not yet replicated"
  • 这是关键的权限管理流程，不能为空
  • 协程体的复刻比预期复杂（线程通信、状态恢复）
  
  教训: 关键路径必须在当前阶段完全实现，不应留空

1. 建立 Stub 方法治理机制
   ──────────────────────
   • 定期搜索所有 "// vendor:", "// No-op", "not yet replicated" 注释
   • 分类: MUST_HAVE (关键路径) vs NICE_TO_HAVE (可选)
   • 关键路径必须在当前阶段补全，可选路径可延后
   • 使用 Lint 规则强制检查

2. 增强代码审查流程
   ──────────────────
   • 引入 @Stub 注解标记 stub 方法
   • 禁止 "// No-op" + 空方法体的组合
   • 改为显式异常或 TODO 注释
   • 协程体必须有实现或明确的 TODO

3. 扩展真机测试覆盖
   ──────────────────
   • 权限申请/恢复场景 (SmartPermissionLossHandler)
   • 设备授权流程 (DeviceAuthorizationManager + yw5xud)
   • WRITE_SETTINGS 权限流程 (resumeWriteSettings)
   • 无障碍事件路由 (AccessibilityEventRouter)

4. 模块依赖梳理
   ──────────────
   • 明确 yw5xud 与上层模块的接口协议
   • 确认 eventFilterManager 是否真的需要
   • 如需要，应优先完成该模块
   • 如不需要，应移除相关调用
